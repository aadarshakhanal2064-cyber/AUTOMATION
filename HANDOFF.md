## 2. What to do first in the new session

1. **Ask the user for the specifics** — ideally screenshots of the generated output next to the original source document, page by page, the same way the formatting-preservation and page-spill bugs were found and fixed this session (see §4 below for that pattern — it works well).
2. Do **not** guess at fixes without seeing what's wrong. Every fix this session came from either a structural diff (table/paragraph counts) or a visual comparison the user provided.
3. Once you know what's misaligned, the fix almost certainly belongs in `tools/bmAgmBuild/build.mjs` — **never hand-edit `assets/templates/bm-agm-minutes.docx` directly**. It's a build artifact; edits there get silently lost the next time anyone reruns the pipeline, and there's no way to tell a hand-edit apart from a real rebuild.

## 3. Rebuilding the template

```bash
cd tools/bmAgmBuild
npm install                     # first time only, or if node_modules is missing
node build.mjs "<path to the firm's real source .docx>"
node fidelity.mjs "<path to the firm's real source .docx>" ../../assets/templates/bm-agm-minutes.docx
```

**Before either script will run, `tools/bmAgmBuild/sample-values.local.mjs` must exist.** It is gitignored on purpose — it holds the real client's name, registration number, chairman's name, and the audit firm's own partner's address, all read off the source document. **This repo is public (CLAUDE.md §1 rule 7) — never put a real value from that file into `build.mjs`, `fidelity.mjs`, a commit message, or this file.** If `sample-values.local.mjs` is missing, both scripts fail immediately with a message pointing at its own header comment, which documents the exact shape to fill in. If it still exists on this machine from this session, leave it alone; if you need to recreate it, read the values off whichever source `.docx` you're working from.

**A real client's source `.docx` is never committed either.** It'll be somewhere outside the repo (this session's was in `C:\CHROME DOWNLOADS\`) — ask the user for its current location if you don't already have a path.

## 4. The pattern that found every bug this session

This is worth repeating because it's what will find the alignment/formatting issues too:

1. **Structural counts, not eyeballing.** `node build.mjs` prints table/cell counts and asserts they match the source; `node fidelity.mjs` asserts the line count and diff count against a known baseline. Both fail loudly on a regression.
2. **Render through the real app path**, not a standalone script, to catch anything the build script's own checks can't see (the page-spill bug only showed up as the app's `bmFitPagesToSheet` silently shrinking a page — the build script's own assertions were all green). Bypass auth via DOM manipulation per CLAUDE.md §12, fill the form via JS, call `bmBuildData()` / `bmRenderDocx()` directly, and check the resulting XML.
3. **Generate a real sample `.docx` and send it to the user** — there's no Word/LibreOffice available server-side, so the user's own visual check in Word is the only way to catch true rendering/alignment issues (font substitution, spacing that renders differently than the XML suggests, etc.). Use `tools/bmAgmBuild/sample-values.local.mjs`'s values (or ask the user which client to use) to fill a realistic sample via `docxtemplater` directly — see the ad-hoc `sample.mjs` pattern used this session (not committed, recreate similarly: load the template with `PizZip`+`Docxtemplater`, `.render(data)`, write the zip out).

## 5. Key gotchas already paid for — don't rediscover these

- **Preeti decoding needs cross-run context.** Decoding a run in isolation (rather than merging adjacent same-formatted runs first) produces garbage or wrong ligatures. `build.mjs`'s formatting-group logic handles this; don't decode run-by-run in isolation if you're touching that code.
- **Runs must be grouped by *visible* formatting, not raw `rPr`.** Word splits runs on metadata that changes nothing on screen (`szCs`, complex-script font, `eastAsia` lang, explicit black colour) — grouping on raw `rPr` split words apart and left the company title unmatched on three pages. See `sigOf()` in `build.mjs`.
- **A value can span runs of different size.** The registration number's separators are smaller than its digits; the company title has a half-size space in the middle. Token replacement works *across* runs (cutting the match from wherever it lives, inserting into the first run touched) rather than merging runs, because merging would move text in paragraphs that use differently-sized space runs as indentation (the declaration pages).
- **Three paragraphs in the source are self-closing** (`<w:p .../>`) — a paragraph regex that doesn't match the self-closing form first will swallow the next real paragraph and shift every subsequent index.
- **The §92 Director's Declaration pages use the company's ABBREVIATED name and slash-separated registration number**, where every other page uses the full name and dandas. That's the firm's own convention on that specific form, not an inconsistency — see `{{companyNameShort}}` / `{{registrationNumberSlash}}` and `bmShortCompanyName()` in `js/bmAgmMinutes.js`.
- **Fiscal years and dates in this template use the danda separator** (`२०८१।८२`, not `०८१/८२`) — `bmFiscalDanda()` / `bmDandaDate()` in `js/bmAgmMinutes.js`. Per-module fiscal-year formats differ by decision (CLAUDE.md §8); don't unify this with another module's format.
- **AGM time is fixed at ०९:०० in the template text** (confirmed with the user, not a token). **There's no audit-fee token** — this template phrases the fee as "by mutual agreement," unlike the old one.

## 6. If something looks structurally fine but still "looks wrong" to the user

Structural checks (table/cell counts, line-diff counts, page-break-style counts) can all pass while something still reads wrong in Word — spacing that renders differently than the XML implies, a font substitution, an indent that's technically present but visually off. That's exactly the gap between "the build script's assertions are green" and "the user says it's misaligned." Don't treat passing assertions as proof of correctness here; they're proof that nothing *regressed* from the known-good baseline, not proof that everything is *right*. Get the user's visual read before declaring anything fixed.
