## 2. Current Architecture

Static site, no bundler. Every dependency is a pinned CDN `<script>` tag (see exact list in §3). Load order in `index.html` matters — files depend on `window.*` globals set up by earlier scripts. Current order: CDN libs → `config.js` → `utils.js` → `js/core/*` (11 engines, in dependency-safe order) → `tabs.js` → feature modules → `auth.js` last (boot sequence).

## 5. VAT Module Status

- **Extraction pipeline:** fixed fractional-coordinate crop boxes (`VAT_FIELD_BOXES`) for the main table, plus a table-bottom-relative "items strip" reader (finds the table's bottom border per page via dark-pixel row scan, then OCRs the strip below it line-by-line and picks the 3-line window satisfying IRD's own `item7 = |item5 - item6|` identity). All digit-only, via `OcrEngine`/Tesseract.
- **Validation:** `ValidationEngine`-driven rule set — VAT-rate (13%) cross-check on sales/purchase/import, total-extraction-failure, all-zero-page, checksum (now blocking when item ५/६/७ are identity-verified and contradict the table), wrong-column-placement warning, duplicate-month, low-confidence-field flagging. Every rule is real, evidence-motivated (see §4/§6), not speculative.
- **Review UI:** editable per-field table with confidence-tier icons + row status badges, plus a separate live "workbook preview" grid (Opening → 12 months → Total, matching the Excel's actual formula chain) with editable Vat Paid overrides and a ✓/⚠️ badge comparing computed Total against IRD's own item ७.
- **Business logic:** `vatBuildMonthRows()` — Difference = D−G−J+L−M, Total = prevTotal+Difference−VatPaid, VatPaid defaults to prevTotal-if-positive-else-0 **but is override-able per month** (see Phase 12.2 discovery above).
- **Excel generation:** fills the real firm template (`assets/templates/vat-detail.xlsx`), verified cell-by-cell identical to the original.
- **Accuracy — reference PDF (the one this whole module is calibrated against):** verified accurate across 6 phases of testing, most recently re-confirmed in Phase 12.4.
- **Accuracy — any other scanner/company:** **not currently supported.** Confirmed via one real second PDF: 9 of 10 pages now correctly block rather than extract wrong numbers; 1 page partially worked (structural/anchor-relative logic partially generalized even there).
- **Performance:** ~7–8 seconds for a full 10-page extraction (reference document), one reused Tesseract worker.
- **Real PDFs tested to date:** the reference Parewashwori PDF (deep, repeated testing); `popular oil distributor` (full pipeline run, mostly fails safe); `COenergyprivatelimited`, `JAY NEPAL KHADYANA`, `NAWA ASHRYA` (structural-validation-only — the latter two are **digital PDFs with real embedded text, not scans**, correctly rejected since they have zero embedded images; a text-extraction path, not OCR, is the right tool for those and does not exist yet).
- **Remaining risks:** (1) single-scanner-profile calibration is the core limitation; (2) the digital-PDF family has no extraction path at all yet; (3) the OCR rewrite investigated this session (§6) has a real evidence-backed recommendation but zero implementation.
- **Can "production-ready" be honestly claimed?** **No, not without the profile qualifier.** For the one calibrated scanner profile: yes, with real verification behind that claim. For anything else: it fails safe today, which is a real, tested, and correct improvement over silently generating wrong numbers — but "supports different scanners/companies" (the user's own stated goal for the rewrite) is not yet true.

## 6. Important Engineering Discoveries

**Scanner/layout:**
- The scanned image sits inside the fixed 595×842pt PDF page at a **per-page-varying vertical margin** (not constant even within one document) — this is why `PdfEngine.getImagePlacement()` reads the actual CTM from the PDF operator list instead of assuming a fixed offset.
- The VAT items-५/६/७ section's position relative to the table's bottom border **also drifts by page** (~0.025 of page height) — a single fixed offset misses on some pages; the current reader retries at 3 offsets and picks the one whose OCR'd text satisfies the form's own arithmetic identity.
- Item ७ (कुल तिर्नु पर्ने कर) is printed **signed** on the form ("+ बा -"); digit-only OCR cannot represent the minus sign, so every cross-check involving it must compare absolute values — this was not documented anywhere before this session and would silently break naive equality checks.
- A genuinely different scanner profile (the `popular` PDF) breaks the fixed-coordinate approach almost entirely — proving the calibration doesn't generalize, which is the actual motivation for the pending rewrite.

**OCR engine behavior (real measurements, not documentation, from the same-day investigation — see §7 for what's pending):**
- Tesseract.js's Devanagari language data (`nep`, `hin`) is **not viable** for this document — measured 15–24% confidence, output is unusable garbage on the exact same crop that PaddleOCR read at 88.5% average similarity to ground truth.
- PaddleOCR (via the third-party `ppu-paddle-ocr` npm package, official PaddleOCR PP-OCRv5 Devanagari model via ONNX Runtime Web/WASM) is genuinely viable for label/text recognition: real measured ~39MB one-time download (dominated by the 26MB ONNX runtime itself, not the models), ~7s cold init / ~2.7s warm (browser HTTP cache), ~0.5–1.8s per whole-table-region recognition, 15→30→36MB memory footprint (not concerning).
- An unplanned but significant finding: PaddleOCR read the SAME "page 3, unreadably poor scan" page that Phase 12 documented as a total extraction failure at 93% confidence with real correct numbers — strong evidence the scan wasn't actually bad, the fixed coordinates were just miscalibrated for that page specifically.
- Real supply-chain risk found: both the JS wrapper (`ppu-paddle-ocr`, ~14 months old, single small company) and its actual ONNX model files (hosted on that same maintainer's own separate GitHub repo, not PaddlePaddle's infrastructure) are a single point of failure. The "official" `@paddleocr/paddleocr-js` package exists but is only 3 months old with undocumented/unconfirmed Devanagari support — checked directly, not assumed.

**Architecture/process discoveries:**
- Extracting an existing pattern into a shared engine is much lower-risk when at least one (ideally two) real, already-working consumer exists to validate against — this project deliberately declined to build speculative APIs (e.g. a generic Excel spec, a generic PaddleOCR pipeline) ahead of a second real consumer, every time.
- "Confidence score" from any OCR engine (Tesseract or PaddleOCR) is a real but imperfect signal — both engines have shown cases of high-confidence wrong reads and low-confidence correct reads. Business logic should always treat confidence as a prioritization hint for human review, never as a correctness guarantee.
- This project's working pattern throughout has been: investigate with real evidence (often live browser testing against real documents, not just reading library docs) → implement only what's justified → verify against real data → regression-check → commit one logical change → get approval before the next. This has held for 16 consecutive commits and should continue.
