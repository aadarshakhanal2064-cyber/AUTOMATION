### 5.11 Company Registrar (topbar dropdown → `regd` group)

**a) BM/AGM Minutes (`js/bmAgmMinutes.js`, `bm-` prefix)** — generates Board Meeting minutes, AGM minutes, the Companies Act §51 capital-structure report, two registrar letters, a Beneficiary Owner declaration and (conditionally) a "Change of Board of Director" set — all ten pages in one Word file, Nepali, generated as LIVE tokens rather than fill-in-the-blank text. Fills `assets/templates/bm-agm-minutes.docx` via DocumentEngine/docxtemplater (`{{token}}` delimiters, `paragraphLoop:true`).

**The build is a MINIMAL-TOUCH transform, and that is a hard rule** (2026-08-20, after the first attempt shipped broken). The firm's source document *is* the format: `buildBmAgm.mjs` rewrites only the text inside runs (Preeti bytes → Unicode, sample values → `{{tokens}}`) and copies every `<w:pPr>`, every `<w:rPr>`, every table wrapper and every tab stop through byte for byte. It must never rebuild a paragraph from a synthesised `<w:pPr>`. The first version did exactly that — it extracted every `<w:p>` and re-joined them as a flat list, silently discarding the `<w:tbl>`/`<w:tr>`/`<w:tc>` wrappers, so the §51 capital report printed as loose unboxed paragraphs instead of the ruled 11-row table the registrar expects. Four more traps sit behind that one, each now guarded by an assertion in the script:

- **Three empty paragraphs are self-closing** (`<w:p …/>`). A naive `<w:p …>…</w:p>` regex swallows the *following* real paragraph, shifting every index past ~195 and silently corrupting the loop anchors. The paragraph regex matches the self-closing form first.
- **Runs are grouped by VISIBLE formatting only.** Word splits runs on metadata that changes nothing on screen (`szCs`, a complex-script font name, an eastAsia language tag, an explicit black `w:color`). Grouping on raw `rPr` split words apart — `अनुमतिले` arrives as two runs and decodes to the wrong vowel when handled separately, and the company title arrives as three runs so `{{companyName}}` never matched it and three pages stayed hard-coded to the sample client.
- **Token replacement works ACROSS runs.** The registration number's `।` separators are two points smaller than its digits, the title has a half-size space in the middle, and the "(Additional Proposal)" placeholder puts its brackets in Preeti and its words in Arial. Merging those runs is not an option — the declaration page uses differently-sized space runs as indentation, so flattening moves the text. Instead the match is cut from whichever runs held it and the token is inserted into the **first** of them, so it inherits the formatting of wherever the value started and every other run keeps its own size.
- **A Preeti syllable can straddle a formatting boundary.** The chairman's name ends bold while the following `को` has its consonant inside the bold run and its vowel sign outside. The script nudges such a boundary a few characters until group-wise decoding equals whole-paragraph decoding, and reports which paragraphs it repaired.

**Pagination is a NAMED STYLE carrying `<w:pageBreakBefore/>` (`BmPageStart`), replacing the source's blank-paragraph spacers** (2026-08-20). The source separates its sub-documents with runs of empty paragraphs and only lands correctly because the sample client's names and figures happen to fill each page to the right height — a longer company name or a fourth director silently pushes a signature block onto the next sheet. `SECTION_STARTS` converts each boundary and drops the spacers that used to do the job. **The three ways of forcing a page break are not interchangeable, and only the style works:**

- A separate `<w:p>` holding `<w:br w:type="page"/>` *is still a paragraph* — its paragraph mark lands at the top of the new page and pushes everything down one line, which is enough to spill the last line of a full page onto the next. This shipped once and is exactly the "content spilled into another page" the user reported.
- Direct `<w:pageBreakBefore/>` in the paragraph's own `pPr` is right for Word, but **docx-preview only reads that property off a paragraph's STYLE** (`splitBySection` → `findStyle(elem.styleName)`), so the app's preview and print saw no breaks at all, rendered ten pages as one section, and `bmFitPagesToSheet` then shrank the whole document onto a single sheet.
- The style satisfies both and adds no content. `BmPageStart` is `basedOn` Normal and sets nothing but the break, so each paragraph's own direct formatting still wins; the build throws if a section-start paragraph ever arrives already carrying a `pStyle`.

**Trailing blank paragraphs are dropped too.** In the source they padded the final declaration page; with the declaration now a loop they land after the *last* iteration and push it 0.8% over a sheet — invisible in a preview that scales to fit, a spilled line in Word.

The boundaries were verified against the source's own `<w:lastRenderedPageBreak/>` markers, which record where Word actually broke: paragraphs 57, 217, 241 and 259. **Paragraph 57 is the AGM's internal break** — निर्णय नं. २ starts a fresh sheet, leaving white space under decision 1, exactly as the firm's file prints — and it is a `SECTION_START` for that reason; 259 is the second Director's Declaration, now produced by the loop. The AGM's *first* page is deliberately not forced: paragraphs 34–55 flow naturally onto it.

Regression guard: the build asserts the table survives, that no sample value is left un-tokenised, and that exactly `SECTION_STARTS.length` paragraphs carry the page-break style. Fit was verified in the running app by checking that `bmFitPagesToSheet` shrinks nothing — every page renders at scale 1.0 with two directors (10 pages) and with five (13 pages).

**Save to database + a searchable Saved-minutes drawer** (2026-08-21) — the same pair Generate Report and Notes to Accounts have, over the same `saved_documents` table and the same shared picker (`ds-` ids). Adding a builder is one value on the `module` CHECK, not a new table and not a second drawer (CLAUDE.md §15) — `db/2026-08-21_saved_documents_bmagm.sql`. Two columns are used differently from the other two callers, both deliberately:

- **`client_id` stays NULL.** It is FK'd to `clients(id)`, and a BM/AGM company is a `registrar_companies` row — the two directories are separate by design (§15: no registrar module reads `window.clientsList`). An id from one would either break the FK or silently point at an unrelated client sharing that id. `client_name` (NOT NULL) carries the company and is what the picker searches.
- **`doc_html` stays NULL.** Report and Notes store rendered HTML because their previews are contenteditable and the hand-edited document *is* what the firm issued. BM/AGM renders a Word file from a tokenised template, so regenerating from `state` reproduces it exactly — there is nothing a stored copy would preserve.

`bmFormState()` / `bmApplyState()` are **one** serialisation shared by the localStorage autosave and the database record; keeping them separate is how a newly added field gets captured by one and missed by the other. `bmApplyState()` clears the extra-shareholder rows before re-adding them, or opening a second saved record stacks its directors under the previous one's (§9), and `bmResetForm()` drops `bmSavedId` so the next Save writes a new row instead of overwriting the record just cleared off screen. Re-saving in the same session amends the same row, matching the other two builders.

**The same Save-to-database + saved-documents drawer was added to the other three registrar document modules later the same day** (2026-08-21, user ask — `db/2026-08-21_saved_documents_registrar_docs.sql` adds `companySecretary`, `auditorChange` and `companyRegistration` to the CHECK). All three follow the BM/AGM rules exactly: `client_id` NULL (a registrar company is not a `clients` row — and Company Registration's company exists in *no* directory yet), `doc_html` NULL (the Word file regenerates from `state` byte-identically), one `xxFormState()`/`xxApplyState()` serialisation shared with the module's localStorage autosave where one exists (`cs`, `cr` — their autosave collect/restore were refactored onto the pair rather than duplicated), `xxResetForm()` drops the saved id, and re-saving amends the same row. Auditor Change still has no autosave (its deliberate trim stands); `acFormState()`/`acApplyState()` are a named pair anyway so a future autosave shares them, and both are **scoped to the panel** because the `ac-` prefix is shared with Add Client (§9's historical overlap). Events: `company_secretary_saved` / `auditor_change_saved` / `company_registration_saved`, labelled in `config.js`.

**Fiscal years and dates use the danda separator** (`२०८१।८२`, `२०८३।०४।२०`) via `bmFiscalDanda()`/`bmDandaDate()`, because that is what the source document writes — not the `०८१/८२` short form `NepaliLocale.fiscalParts()` returns. Per-module fiscal-year formats differ BY DECISION (CLAUDE.md §8); this is BM/AGM's. The one place the source itself writes a slash (`२०८१/८२`, in AGM decision 1) is tokenised to the same `{{fiscalYear}}`, so a generated set is internally consistent where the firm's own file was not.

**Rebuilt from scratch 2026-08-20** against a new source document the firm provided (superseding the original template built 2026-07). **This time the build tooling is committed** — `tools/registrarDocx/buildBmAgm.mjs` — precisely because the *old* pipeline wasn't (`docs/history/HANDOFF.md` §4 documents that gap; don't repeat it). Run `node buildBmAgm.mjs "<path to the firm's real source .docx>"` from `tools/registrarDocx/` to reproduce or extend the template; the source file itself is never committed (real client name/PAN/registration number — CLAUDE.md §1 rule 7) so the path is always external. That subfolder carries its own `package.json` (`preeti-to-unicode`, `preeti`, `jszip`) — the one deliberate exception to this repo's zero-npm-dependency rule, because a one-time Preeti→Unicode decoder is exactly the kind of thing that goes wrong hand-rolled (the old pipeline's multi-day ligature/reph-reordering debugging, same `HANDOFF.md` section). The build script's header comment explains each step; `docs/history/HANDOFF.md` §4–5 is now superseded for BM/AGM specifically (kept for the Preeti-conversion background) — this file is the current record.

**Neither `buildBmAgm.mjs` nor `fidelityBmAgm.mjs` holds a single real sample value as a string literal** — both import them at run time from `tools/registrarDocx/sample-values.local.mjs`, which is gitignored and refuses to exist in git for the same CLAUDE.md §1 rule 7 reason the source `.docx` never does: it names the real client, their registration number, their chairman, and the audit firm's own partner's address, all lifted from a real document. The first version of this build held those values as literals directly in `buildBmAgm.mjs` — caught and fixed before ever reaching `origin/main`, but worth stating plainly: **that file must never be recreated as tracked.** If it's missing, both scripts fail immediately with a message pointing at its header comment, which documents the exact shape to fill in from whichever source document you're rebuilding against.

**Fidelity is proven by a harness, not by eyeballing a page count** — `tools/registrarDocx/fidelityBmAgm.mjs`. It renders the built template with the SOURCE's own sample values and diffs the result against the source line by line, failing if the line count moves or a new difference appears. This is what a page count cannot catch: the first build produced ten pages and was still wrong, with the §51 table flattened and three pages hard-coded to the sample client. Current baseline (as of the 2026-08-20 alignment-fix pass — the harness's own header comment is the source of truth if these drift again): **177 source lines, 174 output lines, 135 identical, 81 diff entries** — every one deliberate (real values redacted here per §1 rule 7):

| Difference (category) | Why |
|---|---|
| a fiscal year's separator | the one place the source writes a fiscal year with a slash instead of a danda; now consistent with every other occurrence |
| one letter in the auditor's name | typo in the source's own auditor-appointment letter |
| the company name and chairman on one page | another client's name, left on the board-change page when that page was copied from their file |
| a vowel sign on a name | dropped in the source, on the board-change minutes |
| "In case of Change of Board of Director" (×3, pure deletions) | a rebuild marker typed into the source, never meant to print — confirmed with the user and stripped |
| every visarga-as-colon (ः → :, ~35 lines / 70 diff entries) | standard Preeti-keyboard habit, not what the firm wants printed — converted everywhere except inside "क्रमशः", where the visarga is part of the actual spelling |

**Word pagination is a separate, measurable thing from everything above, and it was wrong for a long time without any check noticing** (2026-08-20). The `.docx` opened in Word as **19 pages instead of 10** — nearly every sub-document spilling onto a second sheet — while the app's own preview and Save-as-PDF were correct, because the preview *scales each section to fit the sheet* and Word does not. Every structural assertion passed throughout. Word itself is installed and drivable over COM (CLAUDE.md §2), so this was measured rather than guessed; the three causes, each isolated by measurement:

| Change | Pages |
|---|---|
| baseline | 19 |
| + neutralise Word's inherited `pPrDefault` (`after=200 line=276`) | 14 |
| + Nirmala UI instead of Mangal | 13 (11 with both) |
| + §51 table/signature tightened | **10** |

- **The source's `styles.xml` inherits Word's stock paragraph defaults** — 10pt after *every* paragraph plus 15% extra leading. Around 100 paragraphs carry no explicit `<w:spacing>`, so that alone contributed roughly 1000pt (~14in) of whitespace. The original document got away with it because Preeti text is byte-narrow ASCII; real Unicode Devanagari wraps to more lines and stands taller, so the same defaults overflow. `tightDocDefaults()` sets `after=0 line=240`.
- **Mangal is not installed on the firm's machine** (only Nirmala UI is), so Word silently substituted a face with much taller metrics — worth 6 of the 19 pages by itself. `mangalToNirmala()` names the font that is actually present, making the layout deterministic instead of dependent on Word's substitution choice. This is **not** a return to Preeti (CLAUDE.md §15 forbids that) — Nirmala UI is the modern Windows Devanagari font. Like the font scaling, it **must run last**: many of the alignment fixes match on literal `w:ascii="Mangal"`.
- **The §51 capital report still ran one line over**, because its ruled table nearly fills the sheet once the text is real Devanagari, and its signature block is padded by four empty 1.5-spaced paragraphs (the source's way of pushing the signature down the page, which now pushed it off). Shrinking that padding alone was **not** enough — measured, still 11 pages — so `fitSection51()` also takes the table's own text down a further 10%. Both are confined to that one section.

Verified against Word: **10 pages** with two directors, **7** with the board-change toggle off, **13** with five directors — each exactly one sub-document per sheet, and matching the user's own Save-as-PDF page counts. Text and structure are byte-identical to the previous template; only sizes, spacing and font names moved.

**The §92 Director's Declaration pages keep their own company/registration tokens** (`{{companyNameShort}}`, `{{registrationNumberSlash}}`). Those pages use the ABBREVIATED name (`…प्रा. लि.`) and slash-separated registration number where every other page uses the full name and dandas — that is the firm's convention on that form, not an inconsistency, and folding them into `{{companyName}}`/`{{registrationNumber}}` silently printed the long name there. `bmShortCompanyName()` derives the abbreviation so nobody types the name twice; a name already abbreviated, or not a Pvt Ltd at all, passes through unchanged.

**Attendee model changed with the new template**: the source numbers the chairman *and* every shareholder in one list (chairman first, role अध्यक्ष; the rest, role संचालक) — unlike the old template's unnumbered-chairman convention. `bmBuildAttendees()` builds this from the same data as before (`clients.chairman_name` + `clients.shareholder_name` + `client_shareholders`, unchanged), and tags each entry `isChairman` for the two role-conditionals in the Director's Declaration pages. **The Director's Declaration (Companies Act §92(1)) is now a real per-attendee loop**, not a fixed two-page pair — the source had one page for the chairman and a near-identical duplicate for the first shareholder; the build collapses that into one `{{#attendees}}` loop body with an explicit page break **inside** the loop, so every attendee gets their own sheet for any attendee count. Putting that break *before* the loop-open marker instead fires it once and runs the second director's declaration onto the first one's page — a real bug the first pass shipped, caught by rendering a 3-attendee test case.

**`bmGetAllShareholderNames()` drops any shareholder entry matching the chairman's own name** (2026-08-20, user-reported — the chairman was printing twice in the attendee list, once as अध्यक्ष and once again as संचालक). The chairman IS one of the company's shareholders, and `client_shareholders` sometimes lists them again alongside the others; left in, that's a second attendee row for the same physical person. The dedup lives in `bmGetAllShareholderNames()` (the one function `bmBuildAttendees()`, `bmIsSingleShareholder()` and the company-summary shareholder count all read), not in `bmBuildAttendees()` alone, so all three stay consistent with each other. The duplicate row still shows in the form itself (in case the user wants to fix it at the source) — only the generated document's attendee list is filtered.

**New fields this template needs that the old one didn't**: `bm-letterDate` (the registrar letters' own date — distinct from `bm-agmDate` in the source), `bm-termYears` (director reappointment term, defaults to 4), `bm-bmExtraTitle`/`bm-bmExtraDecision` and `bm-agmExtraTitle`/`bm-agmExtraDecision` (each meeting's one case-specific agenda item + its decision — the source's "Additional Proposal" placeholder), and `bm-boardChanged` + `bm-boardChangeDate` (a checkbox gating the entire "Change of Board of Director" block — its own minutes page, a tapsil line in the second registrar letter, and the Director's Declaration loop — behind one `{{#boardChanged}}` conditional in the template, so unchecked cleanly omits all of it rather than three separate toggles that could disagree). **AGM time is fixed at ०९:०० in the template text, not a token** — confirmed with the user; the old `bm-agmTime` field and `{{agmTime}}` token are gone. **No `{{auditFee}}` token exists any more** — this source phrases the audit fee as "by mutual agreement between board and auditor" rather than stating a figure; `bm-auditFee` is gone from the form.

**`REGD_AUDIT_FIRMS` (built in `js/core/orgIdentity.js`) now also carries `address`** — added for this rebuild, since the registrar letter's बोधार्थ (cc) line needs the auditor firm's address alongside its name. Purely additive; every other consumer of that array (Auditor Change's picker) ignores the extra field.

**Capital figures in the §51 report are now live tokens** (`authorizedCapital`/`issuedCapital`/`paidUpCapital`, same `clients` columns as before) — the old template left this table as static sample text from whichever client it was originally built against, a known gap `HANDOFF.md` flagged as a build-tooling limitation, not a design choice; that limitation doesn't exist in the new pipeline. **Share count next to each capital figure ("२५,००० थान") is still static** — deliberately: the old data model never tracked share count as its own field, and this rebuild keeps the same field set rather than opening a schema change mid-rebuild.

**A single-shareholder company never gets a "Change of Board of Director" set** (2026-08-20, user decision) — the chairman-only attendee list already *is* the whole board, so there is no separate board to reappoint. `bmSyncBoardChangedAvailability()` (`js/bmAgmMinutes.js`) disables and force-unchecks `bm-boardChanged` whenever `bmGetAllShareholderNames()` is empty, re-run on every form change (adding/removing a shareholder row can flip this mid-session, not just at company-select time) — and `bmBuildData()` applies the same guard again when composing `boardChanged` for the template, so a stale checked state can never reach a render. The template's own `{{#boardChanged}}` conditional is unaware of shareholder count; the gate is entirely a JS-layer decision.

**The second registrar letter's tapsil (schedule) items 5 and 6 are one combined `{{#boardChanged}}` block, not two** (2026-08-20, user-reported — item 6 used to print unconditionally) — item 5 ("संचालकको पुननियुक्ति सम्बन्धमा") was already gated; item 6 ("दफा ९२, को विवरण", announcing the attached §92 declaration) was not, even though that declaration is itself only generated inside the boardChanged-gated minutes-and-declaration block further down the document (paragraphs 217-255) — so an unchecked box used to leave the letter promising an attachment that was never produced. Paragraphs 185 (item 5) and 186 (item 6) are adjacent in the source with nothing between them, so `buildBmAgm.mjs` wraps them as a single block (`INSERT_BEFORE[185]`/`INSERT_AFTER[186]`) rather than two separate ones — simpler than the item/decision-pair pattern used elsewhere, since there's no "misc" item after 6 that would need renumbering.

**The "Additional Proposal" item/decision is omitted outright when left blank, instead of printing a placeholder** (2026-08-20, user-reported bug — it used to print "२) थप प्रस्ताव छैन" / "छैन ।" as a real numbered item even with nothing typed). `bmHasExtra`/`agmHasExtra` in `bmBuildData()` are `true` only when the user actually typed a title or decision; the template wraps the extra item (paragraph 14 alone) and its matching decision (BM: paragraphs 20+21, a separate heading+content pair; AGM: paragraph 67, heading and content on one paragraph) each in their own `{{#bmHasExtra}}…{{/bmHasExtra}}` / `{{#agmHasExtra}}…{{/agmHasExtra}}` block — two independent blocks per meeting (item, decision), not one spanning both, because AGM's decision block sits several paragraphs after its item and BM's board-change section (paragraphs 160-219) already establishes the "several separately-gated blocks sharing one boolean" pattern.

**The AGM's own item/decision 4 ("संचालकहरुको पुनर्नियुक्ति" — the directors' term ending, reappointed for a new one) is gated on `boardChanged` too, not shown unconditionally** (2026-08-20, user-reported) — it restates on the ordinary agenda exactly what the separate "Change of Board of Director" set formalises, so it only belongs there the year that set is actually generated. Paragraphs 49 (item) and 63-64 (decision heading + content) each get their own `{{#boardChanged}}…{{/boardChanged}}` wrap — two more independent blocks sharing the same flag as the original two (§ above), bringing the template's total to 4 opens/4 closes (`buildBmAgm.mjs` asserts this exactly).

With items/decisions 4 (reappointment) and 5 (extra proposal) both now independently conditional ahead of 6 (विविध, always last), **their own displayed numbers are tokens too, not just विविध's** — `{{agmExtraItemNum}}`/`{{agmExtraDecisionNum}}` read ५ when item 4 is shown, ४ when it isn't (`buildBmAgm.mjs` `PARA_TOKENS[50]`/`[67]`, replacing what was a hardcoded "५)"/"निर्णय नं. ५"). **"विविध" renumbers off BOTH flags** — `{{bmMiscItemNum}}`/`{{bmMiscDecisionNum}}` (BM: ३→२, `agmHasExtra`-equivalent `bmHasExtra` only, BM has no reappointment item) and `{{agmMiscItemNum}}`/`{{agmMiscDecisionNum}}` (AGM: `4 + boardChanged + agmHasExtra`, so anywhere from 4 to 6) are computed in `bmBuildData()`, not read off a fixed offset. All four (boardChanged, agmHasExtra) combinations were verified live in the running app — each renders the correct subset of items 4/5, the correct leftover item's own number, and विविध landing at the correct final position. `buildBmAgm.mjs`'s own regression check asserts the boardChanged/bmHasExtra/agmHasExtra open/close counts and that every renumbering token survived into the built template. `fidelityBmAgm.mjs`'s sample render keeps `boardChanged`/`bmHasExtra`/`agmHasExtra` all true (matching the source, which carries every item) — the renumbered/omitted paths are exercised by the app, not by fidelity-against-the-source.

Client search by registration number/PAN (digit-agnostic) unchanged; live docx preview, autosave draft, completion indicator, zoom, print (one page per sub-document, fitted via the existing font-scaling `bmFitPagesToSheet` — unchanged mechanism, now fitting more page shapes). **Not yet independently proofread by the firm** — the Preeti decode was validated against `org_firms` data and cross-referenced phrase-by-phrase within the document (see `buildBmAgm.mjs`'s CORRECTIONS import), and the rendered output was checked structurally (unzipped, every token confirmed filled, page-break count confirmed to scale with attendee count) — no Word/LibreOffice available to open it visually. The user's plan is to have their senior review a real generated document and report anything to fix.

**c) Company Secretary Appointment (`js/companySecretary.js`, `cs-` prefix)** — became a real module 2026-08-21, replacing the stub added 2026-08-10. Two pages from one form: the board-meeting minutes appointing a company secretary under **Companies Act §84** (required once paid-up or subscribed capital reaches Rs 1 crore), and the notification letter to the Company Registrar's Office. Fills `assets/templates/company-secretary-appointment.docx` through DocumentEngine/docxtemplater, same architecture as BM/AGM — live docx-preview, Save as Word, Save as PDF/Print, autosave draft, completion indicator, zoom, B.S. date validation, and (since 2026-08-21) Save to database + a Saved appointments drawer (see the shared note under BM/AGM above).

Deliberately a much smaller module than BM/AGM: that document is ten sub-documents with four conditional blocks and renumbering agenda items, this one is two fixed pages, so there is nothing to gate or renumber. The only list is the attendees.

- **The company name on page 2 was NOT highlighted in the firm's source**, unlike every other fill-in spot. It is a token anyway — left alone it would have printed the sample client's name on the letterhead of every generated letter, which is exactly the bug the BM/AGM rebuild hit on three pages. `buildCsAppoint.mjs` asserts `{{companyName}}` appears **twice**.
- **`प्रा.लि.नं.` and the letter's `मिति` are tokens too** (user-requested — they were blanks/sample text in the source). The letter date is a *separate field* from the meeting date even though the source has them equal, because a letter routinely goes out days after the meeting; it and the appointment date both **fall back to the meeting date when left blank**, which is what keeps the common case to one date instead of three.
- **The attendance list is a `{{#attendees}}` loop against a real tab stop**, not two hard-coded rows. The source aligns its two names with literal spaces — five on one row, nine on the other — which line up for exactly that pair of names and nothing else. Verified in the running app: with names of different lengths both role columns start at the same pixel.
- **Five alignment blocks were rebuilt on real Word properties** (the source positions everything with hand-typed spaces and tab presses): the attendance rows, the letter date line (53 leading spaces → right-aligned), the signature block (three paragraphs, 55/54/54 leading spaces, no `w:jc` at all → one shared **left** indent), the inner subject line, and the two-line बोधार्थ block (→ real indent, one shared size). Each is an exact-string swap that **throws** if the source changes, so a re-typed source fails loudly rather than silently printing the old spacing.
- **The signature block is LEFT-aligned on a shared indent, not centred** (2026-08-21, user-reported after the first version shipped centred). Centring it is mathematically "aligned" — Word reports the same indent and the same centre on all three lines — but the three are deliberately different sizes (16pt underlined label, 18pt bold name, 18pt title), so centred lines each *start* at a different x and the block reads as crooked. The source's own 55/54/54 leading spaces are a left-alignment attempt that space-counting could not quite land, so left-aligning is also what it was reaching for. `buildCsAppoint.mjs` asserts no `<w:jc>` survives on those three paragraphs.
- **One of the three blank paragraphs between "निवेदक" and the name is dropped** (2026-08-21, same report — "too far away"). Three is a signing gap wide enough that the label stops reading as part of the same block: measured in Word at 54.5pt from label to name while the name and its title sat 21.5pt apart, which looked lopsided. Two blanks leave ~23pt of white — still real room to sign above the printed name, tight enough that the four lines read as one block.
- **The meeting time is an editable field, not fixed template text** — unlike BM/AGM's AGM time, which the user asked to fix. A board meeting's hour is not conventional the way an AGM's is. It is pre-filled with `बिहान १० बजे`, so the common case is still no typing.
- **Font sizes are an explicit table, not a scale factor** (2026-08-21, sizes given by the firm): company name 16pt, letter subject line and `महोदय,` 14pt, everything else — body, subtitle, `प्रा.लि.नं.`, the letter's `मिति`, `निवेदक` — 11pt. `CS_SIZES` in `buildCsAppoint.mjs` maps source half-points to targets and `remapFontSizes()` applies it verbatim. A single factor cannot express these (the body drops by nearly half while the title drops by a quarter), and approximating it with a factor plus per-element patches is how a size hierarchy drifts out of step with itself. The build **fails** on any source size with no entry, and on any size in the built body that isn't one of the targets — an unmapped size would otherwise ship at its original Preeti-era value, 50% too big, right beside correctly-sized text.
- **Body line height is 1.40, and the spacer paragraphs are pinned so they don't inherit it** (2026-08-21, user-reported — "everything feels so close"). The long decision paragraphs wrap to 7–11 lines each, and at the earlier 1.10 those lines sat close enough that Devanagari matras from one nearly met the next. Raising it exposed a trap worth remembering: the 17 empty spacer paragraphs on the letter page inherit line height like any other paragraph, so opening up the body silently multiplied every gap too and pushed the बोधार्थ block onto the bottom margin (measured at 730pt into a 720pt page). `shrinkEmptyParagraphs()` now sets each spacer's own single line spacing as well as its size, so **gap height and reading leading are two independent knobs**. Measured after: all four pages across both test shapes land between 568pt and 662pt of 720pt usable.
- **Word pagination was measured, not assumed** — see `buildCsAppoint.mjs`'s footer for the full grid. Two separate causes had to be fixed before any font scale worked: the 17 empty spacer paragraphs on page 2 (until those shrank, the *letter* overflowed and no scale down to 0.78 fixed it), and Word's inherited 1.15 line height (four lines of pure leading on a 28-line page, which is what the minutes' closing decision needed). Superseded 2026-08-21 by the explicit size table above; the measured grid that produced the original 0.80/264 is kept in the build script's footer because it is the record of *why* the source's own sizes cannot be used. Still verified at 2 pages for both a 2-director and a 5-director board with deliberately long names. Six directors legitimately becomes 3 pages — a bigger board is more minutes — and the letter still starts on its own sheet regardless, because `CsPageStart` forces it.
- **`<w:proofErr>` stripping was the correctness fix that mattered**, and it is in `core.mjs` because it is general. This source carries **506** of Word's spell-check markers, 141 in a single paragraph. They render nothing but sit *between* runs, so identically-formatted runs stopped being adjacent, landed in different formatting groups, and Preeti ligatures decoded across the split — 8 paragraphs disagreed with their own whole-paragraph decode and produced real misspellings (`कम्फनी` for `कम्पनी`, `दफmा` for `दफा`). Stripping them takes that to one paragraph, which the boundary-nudge repair handles. The BM/AGM source carries none, which is why that pipeline never saw it.
- **One accepted decode mismatch remains** (the letter's inner subject line) and is listed by paragraph number in `buildCsAppoint.mjs` rather than silenced: its runs decode correctly one by one while the whole paragraph decodes `कम्फनी`, so the run-by-run result is the right one and ships. A mismatch in any *other* paragraph still fails the build.
- **Colon separators are normalised**, same user decision as BM/AGM: the visarga (`ः`) the Preeti keyboard produces becomes an ASCII colon, and the space before it is closed up — the source has a space in six places and not in the seventh, printing the same label two ways on one page.

**d) Company Registration (`js/companyRegistration.js`, `cr-` prefix)** — became a real module 2026-08-20, replacing the last registrar stub. `js/registrar.js` (the `moduleComingSoon()` holder) went with it — **no stubs remain**. (Party Ledger graduated from that stub 2026-07-26; Share Transfer, Increase Capital and PIN Reset were removed 2026-08-10 — the firm doesn't do that work.)

Save to database + a Saved registrations drawer since 2026-08-21 (see the shared note under BM/AGM above). Generates the complete incorporation filing as ONE Word file, four sub-documents: **Memorandum of Association (प्रबन्ध पत्र, दफा १८(६))** → **Articles of Association (नियमावली)** → **application letter to the Company Registrar's Office** → **power of attorney (मन्जुरीनामा)**. Same DocumentEngine/docxtemplater architecture and preview kit as BM/AGM and Company Secretary. Built from TWO of the firm's real Preeti sources by `tools/registrarDocx/buildCompanyReg.mjs` (multi-shareholder + single-man), with `fidelityCompanyReg.mjs` and `sampleCompanyReg.mjs` as its committed harnesses; page counts are measured, not assumed (9 sheets single / 17 multi at 2 and at 5 founders — the build script's footer holds the line-height grid).

- **TWO templates, selected automatically by founder count — never a toggle** (user decision 2026-08-20). The two sources differ in wording throughout (singular declarations, no साधारण सभा/board rules, a परिच्छेद chapter structure in the single-man AOA), so one founder loads `company-registration-single.docx` and two or more load `company-registration-multi.docx`. The form shows which set will generate.
- **No company picker, uniquely among the registrar screens** — the company being registered exists in no directory yet. The optional **"Add to Company Register"** button closes the loop *after* the firm actually files: one explicit click (admin-only, same RLS rule as Company Profile's add) inserts the `registrar_companies` row (registration number left blank — the registrar assigns it) plus `registrar_shareholders` rows for founders 3+, then `RegistrarDirectory.reload()`. Never automatic — a generated draft is not a registered company — and Company Profile remains the only screen that EDITS a register row.
- **Shares are derived at रु १००/share, never typed as counts** (user decision) — 5,00,000 capital IS 5,000 शेयर, on all three capital rows. Each founder's subscribed shares are **pre-filled as an equal split of the issued shares, editable per founder** — an auto pass never overwrites a hand-typed count (`data-auto`), and a mismatch against the issued total shows a warning naming both figures.
- **Every amount-in-words bracket is derived from the figure** (`NepaliLocale.amountToWords`, added for this module) — the sources' own brackets carry real mistakes ("पाँच हजार रुपैया" beside the 5-lakh issued figure; rupee words after a share count), which never reach a generated document. Spelled रुपैयाँ.
- **The ईति सम्वत line is one typed date** — month name AND weekday (रोज) derive from it via `NepaliLocale.bsWeekday` (anchored 1 Baishakh 2080 = Friday, verified against the multi source's own "भदौ ०२ गते रोज ०३"). Dates print with danda separators (BM/AGM's convention). The letter date is its own field, falling back to the document date.
- **The founders' subscription table is a docxtemplater ROW loop** — `{{#founders}}` opens in the data row's first cell and closes in its last, which docxtemplater expands to repeat the whole `<w:tr>` (verified empirically before building on it). The multi source's second hard-coded founder row is removed **structurally, as a whole row** — dropping only its paragraphs would leave `<w:tc>` elements with no `<w:p>`, which is invalid OOXML.
- **Every numbered point keeps itself whole across page breaks** (2026-08-21, user ask) — `keepPointsTogether()` in the build sets `<w:keepLines/>` on every content paragraph (its lines never split; Word's own exception still lets a paragraph genuinely taller than a page flow on, which the user explicitly allowed) and `<w:keepNext/>` on every paragraph whose successor belongs to the same point, so a दफा with sub-clauses moves whole to the next sheet. **Telling a new top-level point from a sub-item is the subtle part** — both can be numbered "१." in these sources — and the rule that holds for both documents is: dot-numbered AND continuing the running sequence (`topCounter + 1`) is a new point; paren forms (`(१)`, `१)`) and out-of-sequence numbers are content of the current one. The counter resets at every `CrPageStart` (each sub-document restarts at १); blanks and loop-marker paragraphs break a chain, so rendered loop iterations never weld to each other. **The declaration + founders table + मस्यौदाकार block is one chained signature unit** (second user report, same day — the two-founder table broke between its rows, and the declaration separated from its own table): the declaration paragraph binds INTO the table, every row's paragraphs carry keepNext (the loop copies them per founder), and the last row binds onward into the drafter block. Costs: multi went 17→18 pages (2 founders) and 17→22 (5). Verified over COM: **zero paragraphs span a page boundary**, every multi content page begins with a numbered point heading, and the signature units sit on ONE page in the single and 2-founder samples — a 5-founder unit legitimately spans, the same "genuinely too long" exception.
- **The table keeps itself together across page breaks — and the fix that mattered was UN-FLOATING it** (2026-08-21, user-reported — the header row printed at the foot of one page with the founder row on the next). Both sources' founders tables are text-anchored FLOATING tables (`<w:tblpPr … w:tblpY="177"/>`), and **a positioned table ignores every pagination keep rule**: `cantSplit` and `keepNext` were set, Word's own COM reported them parsed (`KeepWithNext=-1`, `AllowBreakAcrossPages=0`), and the table split anyway — five property experiments all failed identically before the anchor was found. The build now strips the anchor (the centred position survives as a real `<w:jc w:val="center"/>` on the table) and keeps the belt-and-braces row properties: `<w:cantSplit/>` on every row (the single source already carried it; the multi needed it added after `tblPrEx`, its schema position) and `<w:keepNext/>` on every header-row paragraph. A many-founder table may still break BETWEEN founder rows, which is correct — each row moves whole. Verified over COM: `Rows(1)` and `Rows(2)` report the same page in every founders table across all three sample shapes, at unchanged page counts (9/17/17). The build fails if a `tblpPr` ever survives. The letter/POA signature blocks loop founder **pairs** (two names per row, real tab stops at 720/4680 twips replacing the hand-counted spacing, `{{#hasRight}}` leaving an odd count's last right column empty).
- **The single source's letter and POA pages were stale copies of the multi client's file** — still carrying the other company's name, founders and advocate. Tokenised like any other sample values, and the wording switched to the **singular** (म…छु / मेरो — user decision 2026-08-20); the multi letter keeps its own wording untouched apart from tokens.
- **Preview and print use `fitPagesToSheet`'s `flow` mode, not one-sheet fitting** — the MOA and AOA genuinely span several sheets, and the fitting that is right for BM/AGM (every section one sheet by design) would bisect these to half size and clip them. **`DocumentEngine.paginateFlowSections` then splits each flow section into real A4 sheets by the same rules the Word file carries** (2026-08-21, user ask — "the way page breaks work in Word, make the same at preview and save as PDF"): it reads every block's `<w:keepNext/>` out of the generated blob itself, welds keep-chains and tables into atomic units, and moves whole units onto pages. Two renderer-parity findings live in that function: (a) Word's `lineRule="auto"` spacing is value/240 × the FONT'S own single-line metric (~1.36em for Nirmala UI) while docx-preview maps the same value to a flat CSS line-height — uncorrected, the browser packed ⅓ more lines per page and broke three pages early; with the `LINE_METRIC` correction the preview's page count **equals Word's exactly** (18/18 on the 2-founder parity document, 12 of 18 page-starts identical, the rest off by one point); (b) if the rendered block list ever disagrees with the document's, it falls back to per-block pagination (paragraphs and tables still never split) rather than mis-assigning keep flags. The print window prints the same page sections one per sheet, with `break-inside: avoid` hints covering the only case a page can overrun — a unit genuinely taller than a sheet.
- **`correctionsCr.mjs` is its own list, deliberately NOT the shared BM/AGM CORRECTIONS** — that list was verified against a different corpus, and its `'वारे'→'बारे'` rule would corrupt "वारेस" (four occurrences in the POA here). Every CR entry was verified against a correctly-spelled occurrence in this document pair.
- **Both templates are A4** (the multi source was US Letter — no Nepali registrar takes Letter), body 11pt at 1.30 line height, an explicit size table per source (the CS_SIZES idiom).
- **Source mistakes found and their dispositions**: the single AOA header cites "दफा ४ को उपदफा (२)" where the multi cites "दफा २० को उपदफा (४)" for the same document — **kept verbatim, flagged for the firm to confirm**; a stray "डौं" fragment in the multi witness cells — dropped; the wrong bracket words — superseded by derivation; `कम्फनी`-class Preeti decode errors — corrected via the corrections list, each verified against the same corpus.
- The `expectedDiffs` lists the fidelity harness matches against live in the **gitignored** `sample-values-cr.local.mjs`, not in the committed harness — the substrings quote real founder names and a citizenship number, which is exactly the leak-through-docs door the playbook's Phase 6 warns about (and this build nearly walked through it before the pre-commit grep).

**e) Company Profile (`js/companyProfile.js`, `cp-` prefix)** — **the firm's register of Nepalese companies, and the only screen that adds, edits or deletes one.** Rewritten 2026-08-20 from an edit-only form into a full directory.

*What it was, and why it changed.* Added 2026-07-27 as the new home for the seven statutory fields removed from the general Add/Edit Client form (§5.7). Those fields lived on `clients` rows, so this screen searched the client directory — and so did every other picker in the app, which meant a Devanagari company name surfaced in Bank Entry, Service Memo, Work Done, Autobooks, Confirmation and Generate Report, where nothing can be done with one. There was also no way to ADD a company: you could only fill in details for a row that already existed. Both were fixed at once by moving the records out of `clients` entirely (`db/2026-08-20_registrar_companies.sql`, CLAUDE.md §15).

*Where the data lives now.* `registrar_companies` (name, registration number, PAN, chairman, shareholder, the three capitals, address, country, notes) and `registrar_shareholders` (one row per additional shareholder/director, `sort_order`ed). Both org-scoped with RLS from birth; adding and deleting a company are admin-only, mirroring `clients`, while editing details and managing shareholders are open to every member. The old `client_shareholders` table was dropped in the same migration — all 55 of its rows belonged to companies that moved.

*How it is read.* Never directly. `js/registrarCompanies.js` loads both tables at sign-in into `window.registrarCompanies` (shareholders nested on each company as `.shareholders`) and exposes `RegistrarDirectory`:

| Call | Does |
|---|---|
| `list()` / `byId(id)` | the register, or one company |
| `shareholders(id)` | that company's extra rows, always an array |
| `attendeeNames(id)` | fixed shareholder + extra rows, **with the chairman's own name dropped** — that dedup used to be duplicated in BM/AGM and Company Secretary, and without it the chairman prints twice in an attendee list (once as अध्यक्ष, once as संचालक) |
| `attachCompanyPicker(input, list, opts)` | the one company autocomplete. Digit-agnostic normalization is baked in (registration numbers and PANs are stored in Devanagari numerals while people type English digits), which each of the four registrar screens used to keep its own `xxToEnglishDigits` copy of |
| `reload()` / `onChange(fn)` | refetch, and redraw anything on screen when it changes |

*The isolation rule.* No non-registrar module may read `window.registrarCompanies`, and no registrar module reads `window.clientsList`. Verified live: BM/AGM, Company Secretary and Auditor Change all find a seeded company, while Generate Report, Service Memo, Confirmation and Bank Entry find nothing for it and still find real clients.

*The screen.* A Tabulator directory (company, registration number, PAN, chairman, shareholder count, paid-up capital, Edit/Delete) over a search box that filters by plain substring — not Fuse, because the user is filtering a list already on screen and a half-typed registration number must not fuzzy-match another company's PAN. A four-card stat strip counts companies, how many are **Ready to Generate**, how many are missing details, and how many have shareholders. `+ Add Company` and `Edit` open the same slide-down editor; its inputs are BUILT from `CP_FIELDS`, so a new field is one line. The completeness meter counts only `required` fields — the ones a registrar document actually prints — so "incomplete" means "this would print blanks", and the directory badges such a row. Shareholders are edited as add/remove rows and **replaced wholesale on save** (delete-then-insert scoped to the one company): the rows on screen are the list. Events logged: `registrar_company_added` / `registrar_company_saved` / `registrar_company_deleted` (the pre-2026-08-20 `company_profile_saved` label is kept in `config.js` so historical rows still read as words).

*Bulk import.* `Import from Excel` opens the same wizard the Clients tab uses, under the `registrar` profile in `window.IMPORT_PROFILES` — the firm's own company sheets list every shareholder on its own row beneath the company, and that handling is in the shared wizard, not duplicated here. The two profiles' field lists are disjoint, so a company sheet cannot be imported into the client directory or vice versa.

*VAT status is no longer on this screen.* `clients.vat_status` is a property of an audit client (whether the firm files its monthly VAT return), not of a company-registration record, and all 45 registrar rows had it at its default. It stayed on `clients`; it simply has no editor at present, since its last reader went with the VAT Compliance module in 2026-08-10. Put it on the Clients edit form if it is ever wanted again — not here.
